================================================================================
FLY BIRDY — NESTED EXECUTION TRACE (code A -> calls code B -> calls code C ...)
================================================================================
Format used below for every trace:

[filename] CODE A — what it is (function/button/screen/handler)
<code for A>
    |
    v  (A's output is fed into / A calls...)
    [filename] CODE B — what it is  (this call happens INSIDE code A)
    <code for B, indented one level>
        |
        v
        [filename] CODE C — what it is (this call happens INSIDE code B)
        <code for C, indented two levels>
        => DISPLAYS/DOES: one-line result of C
    => DISPLAYS/DOES: one-line result of B (after C returns/runs)
=> DISPLAYS/DOES: one-line result of A (after B returns/runs)

Read top-to-bottom, indentation = call depth (nesting), exactly like the
example you gave (code A -> code B is called inside A -> rest of A -> result).
Order below = the order screens actually load for a player.

================================================================================
LEGEND / HOW TO READ NESTING ABOVE
================================================================================
- Indentation level = call depth. A block indented once deeper than its
  parent means "this function/handler is invoked from inside the parent's
  code body," exactly like your example:
      code A (some .html)
          code B (some .js, receives code A's element as input)
              code C (called inside code B)
          rest of B
      => what A causes to happen on screen, in one line
- "=> DOES / DISPLAYS" always summarizes the RETURN VALUE or ON-SCREEN
  EFFECT of the block directly above it, once its own nested calls (if any)
  have finished running.
- Where a nested call happens on a LATER frame/event (e.g. a button's stored
  action, which only runs the next time the player taps something) this is
  called out explicitly, since it is not a same-frame nested call.
